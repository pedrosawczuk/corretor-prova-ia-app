# TASKS — Integração de pagamentos (AbacatePay)

Escopo: sair do zero até assinatura/pagamento avulso funcionando em produção, cobrindo os 3 planos definidos (Avulso, Essencial, Pro) sobre a métrica de uso **correções processadas** (1 correção = 1 `submission` criada).

Prioridade: **P0** (bloqueia lançamento), **P1** (necessário antes de abrir pra usuário real, mas não trava o primeiro deploy em sandbox), **P2** (pode entrar depois do primeiro cliente pagante).

Convenção de nomes de plano usada nas tarefas: `avulso` (pacote de créditos, cobrança única), `essencial` e `pro` (assinatura recorrente mensal).

## 0. Decisões e pontos em aberto (resolver antes ou durante a implementação)

Isso não são tarefas de código — são bloqueios de informação. Marcados explicitamente porque não tenho certeza suficiente pra virar tarefa acionável sem confirmação.

> Detalhamento completo (payloads, exemplos, código) de cada item resolvido abaixo está em [`docs/billing-abacatepay.md`](./docs/billing-abacatepay.md).

- [x] **[RESOLVIDO — API AbacatePay]** Não existe SDK Node oficial estável recomendável agora: `abacatepay-nodejs-sdk` está oficialmente descontinuado (usa API v1, incompatível com os endpoints atuais); o sucessor `@abacatepay/sdk` existe mas sem maturidade confirmada. **Decisão: integração via REST puro com `fetch`**, seguindo o padrão de wrapper fino já usado em `gemini.ts`/`storage.ts`.
- [x] **[RESOLVIDO — API AbacatePay]** A API pública atual é a **v2** (`https://api.abacatepay.com/v2`) e não usa `frequency: MULTIPLE_PAYMENTS` (isso era da v1). Cobrança recorrente exige um **produto pré-cadastrado** (`POST /products/create`) com campo `cycle` (`WEEKLY`|`MONTHLY`|`QUARTERLY`|`SEMIANNUALLY`|`ANNUALLY`) — o ciclo é propriedade do produto, não da assinatura. `POST /subscriptions/create` referencia esse `id` de produto em `items` (exatamente 1 item) e devolve um checkout; a assinatura (`subs_...`) só passa a existir após o pagamento, confirmado via webhook `subscription.completed`. **Isso muda a suposição dos blocos 2+ do TASKS.md — usar os payloads reais documentados em `docs/billing-abacatepay.md` ao implementá-los.**
- [x] **[RESOLVIDO — API AbacatePay]** Cancelamento: `POST /subscriptions/cancel` com `{ id: "subs_..." }`. Cancela **imediatamente** no lado da AbacatePay (sem carência) — a lógica de "acesso até o fim do ciclo pago" (bloco 8.4) é responsabilidade nossa (`cancelAtPeriodEnd` local), não da API.
- [x] **[RESOLVIDO — API AbacatePay]** Enumeração fechada de 18 eventos confirmada (grupos: `checkout.*`, `transparent.*`, `subscription.*`, `payout.*`/`transfer.*`). Renovação de ciclo recorrente **dispara um evento próprio**, `subscription.renewed`, distinto de `subscription.completed` (primeira ativação) e de `subscription.cancelled`. Lista completa em `docs/billing-abacatepay.md`.
- [x] **[RESOLVIDO — API AbacatePay]** A verificação de assinatura (`X-Webhook-Signature`, HMAC-SHA256 sobre o raw body) usa um **segredo separado** — o `secret` informado por nós no `POST /webhooks/create`, **não** o `ABACATEPAY_API_KEY`. Mapeado para `ABACATEPAY_WEBHOOK_SECRET`.
- [x] **[DECISÃO DE PRODUTO]** Uma correção que falha no processamento (foto ilegível, erro da IA) consome 1 unidade da cota do plano — **confirmado com o time**: consome no momento da criação da `submission`, sem lógica de estorno.
- [x] **[DECISÃO DE PRODUTO]** Upgrade/downgrade de plano no meio do ciclo — **confirmado com o time**: sem prorate, a troca vale a partir da próxima renovação (ver bloco 7).
- [ ] **[DECISÃO DE PRODUTO — ainda aberto]** Valores finais (R$39,90 / R$99,90 / pacote avulso) são hipótese baseada em concorrência, não em custo real por correção. Não travar os números em copy de marketing/checkout até confirmar custo de IA de visão + storage por correção. Não bloqueia a implementação técnica dos blocos 1-8 (só a tarefa 9.1 de copy/preço na página pública).
