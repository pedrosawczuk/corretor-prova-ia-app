# TASKS — Auditoria de segurança (correção)

Gerado a partir de uma análise completa do projeto: stack (Fastify + better-auth + Drizzle/Postgres no backend, Next.js no frontend, Redis, MinIO, monorepo pnpm/turbo), pontos de entrada (rotas REST de auth/admin/classrooms/exams/submissions/billing, webhook do AbacatePay, upload multipart), fluxo de autenticação/autorização, dependências (`pnpm audit` nas duas apps) e modelo de dados (campos sensíveis em `user`, `account`, `two_factor`, `correction_credits`, `subscriptions`).

Áreas auditadas e **já implementadas corretamente** (nenhuma tarefa criada de propósito): hashing/política de senha e 2FA via `better-auth`, checagem de ownership (IDOR) em `classrooms`/`exams`/`submissions`, guarda extra em rotas admin do `better-auth` (`guard-admin-auth-routes.ts`), validação de tipo real de arquivo por magic bytes (`file-type`) em uploads, nomes de objeto gerados no servidor (sem path traversal), URLs pré-assinadas do MinIO com expiração de 1h, CORS restrito a `WEB_URL`, Helmet com CSP `default-src: none`, rate limiting global + agressivo em rotas sensíveis de auth, verificação de assinatura HMAC (`timingSafeEqual`) no webhook de billing, e sanitização de payload sensível no log de auditoria.

Ordenado por severidade real, mais crítico primeiro.

---

## Alta severidade

- [x] **Upgrade de plano sem recobrança correspondente permite escalar privilégio de faturamento indefinidamente**
  - Onde: `apps/api/src/modules/billing/change-plan.ts` (fluxo `immediate: false`, linhas ~51-66) e `apps/api/src/modules/billing/billing-webhook.ts` (case `subscription.completed`/`subscription.renewed`, promoção de `pendingPlanId` para `planId`)
  - Problema: quando `change-plan` é chamado com `immediate: false` (padrão), o código só grava `pendingPlanId` — nunca atualiza o valor cobrado pela AbacatePay na assinatura (`abacatepayBillingId` não muda) — e no próximo `subscription.renewed` o webhook promove `planId` para o plano mais caro incondicionalmente, concedendo os limites/benefícios do plano superior enquanto o usuário continua sendo cobrado o preço do plano antigo (mais barato) em todos os ciclos seguintes.
  - Critério de pronto: um usuário assinante do plano `essencial` que chama `POST /billing/change-plan` com `{ planSlug: "pro", immediate: false }` só recebe os benefícios do `pro` depois que o valor efetivamente cobrado na AbacatePay muda para o preço do `pro` (via checkout/atualização de assinatura na cobrança seguinte) — nunca antes disso. Deve existir teste cobrindo que uma promoção de plano no webhook só ocorre quando o preço cobrado corresponde ao `pendingPlanId`, e teste de regressão para o caso de downgrade (que não deve travar).
  - **Feito:** `billing-webhook.ts` não promove mais `pendingPlanId` incondicionalmente. Ao receber `subscription.completed`/`subscription.renewed` com `pendingPlanId` setado, busca o preço (`priceCents`) do plano atual e do pendente e só promove se (a) for downgrade/lateral (`pendingPlan.priceCents <= currentPlan.priceCents` — não há escalada de privilégio, então não precisa de confirmação de cobrança) ou (b) o valor cobrado no evento (`data.amount`, em centavos, seguindo a convenção da AbacatePay) corresponder exatamente ao preço do plano pendente (caso de upgrade). Caso contrário mantém o plano e o `pendingPlanId` como estavam e loga um aviso, sem travar o webhook (responde 200 normalmente). Testes novos/ajustados em `billing-webhook.test.ts`: promoção de upgrade quando o valor cobrado bate, não-promoção de upgrade quando o valor cobrado ainda é o do plano antigo, e promoção de downgrade mesmo sem o valor cobrado mudar (regressão).
  - **Nota (não é bug, é limitação de dados externos):** o nome do campo `data.amount` no payload do webhook de assinatura da AbacatePay é uma inferência (assim como `data.metadata.userId/planSlug`, já assumido no código antes desta tarefa) — a doc `docs/billing-abacatepay.md` (seção 2.3) já registra que esse formato não é oficialmente documentado. Se o campo real tiver outro nome, um upgrade nunca vai promover automaticamente (fica preso em `pendingPlanId`, sem downgrade indevido nem escalada) até validar contra o payload real da sandbox — mais seguro do que o comportamento anterior, mas vale confirmar o nome do campo assim que houver acesso à sandbox real.

## Média severidade

- [x] **Condição de corrida (TOCTOU) permite consumir mais correções do que o plano ou o saldo de créditos permite**
  - Onde: `apps/api/src/modules/billing/assert-correction-quota-available.ts` (função `assertCorrectionQuotaAvailable`), chamada em `apps/api/src/modules/submissions/create-submission.ts`
  - Problema: a checagem de cota mensal (contagem de submissões vs. limite do plano) e a checagem/consumo de crédito avulso (`SELECT` de saldo seguido de `INSERT` de `-1`) não são atômicas nem protegidas por lock/transação — requisições concorrentes leem o mesmo saldo/contagem antes de qualquer uma delas ser persistida, permitindo múltiplas submissões aprovadas com apenas 1 crédito ou 1 vaga de cota restante.
  - Critério de pronto: disparar N requisições concorrentes de `POST /exams/:examId/submissions` para um usuário com exatamente 1 crédito (ou 1 vaga de cota) restante resulta em no máximo 1 submissão criada; as demais recebem `PaymentRequiredError`. Implementado via transação com `SELECT ... FOR UPDATE` no saldo/assinatura, ou via `UPDATE` condicional atômico (`WHERE saldo >= 1 RETURNING`) antes de permitir a criação da submissão. Deve haver teste de concorrência (ou teste de integração simulando duas chamadas na mesma transação) cobrindo o caso.
  - **Feito:** `assertCorrectionQuotaAvailable` passou a receber a transação (`tx`) do chamador em vez de usar o `db` global, e a primeira coisa que faz dentro dela é `SELECT ... FROM "user" WHERE id = $userId FOR UPDATE` — isso serializa (via lock de linha do Postgres) todas as chamadas concorrentes da função para o mesmo usuário. `create-submission.ts` agora chama `assertCorrectionQuotaAvailable(tx, user.id)` e o `INSERT` da submissão dentro do mesmo `db.transaction`, então a leitura de cota/crédito, o consumo do crédito avulso e a criação da submissão só são liberados/commitados como uma unidade atômica por usuário — uma segunda requisição concorrente só enxerga a contagem/saldo depois que a primeira transação (que já fez o `INSERT`) terminar. Isso corrige tanto a corrida da cota mensal (o `INSERT` da submissão que altera a contagem passou a ficar dentro do mesmo lock) quanto a do crédito avulso. Ajustado `apps/api/src/test/create-db-chain.ts` (adicionado `for` à lista de métodos encadeáveis do mock) para suportar o `.for('update')` nos testes. Testes: `assert-correction-quota-available.test.ts` cobre o lock (`for('update')` chamado antes de qualquer outra query) e tem um teste de "duas chamadas sequenciais compartilhando a mesma transação" simulando a serialização — a segunda só vê o saldo já consumido pela primeira e é rejeitada com `PaymentRequiredError`; `create-submission.test.ts` ajustado para o insert acontecer via `db.transaction`.
  - **Nota:** não foi possível rodar um teste de concorrência real contra Postgres (toda a suíte de `apps/api` usa `@app/db` totalmente mockado via `vi.mock` em `src/test/setup.ts` — nenhum teste do app roda contra banco real, diferente do que `docs/code-patterns-backend.md` seção 6 descreve; sinalizando essa divergência entre doc e código real ao final, sem alterar o `docs/`). O teste de concorrência aqui é uma simulação (duas chamadas sequenciais no mesmo mock de transação, validando que a segunda vê o efeito da primeira), não um teste de carga com requisições HTTP paralelas reais.

- [x] **Tokens OAuth (Google) armazenados em texto plano no banco**
  - Onde: `packages/db/src/schema/accounts.ts` (colunas `accessToken`, `refreshToken`, `idToken` da tabela `account`)
  - Problema: os tokens de acesso/refresh do provedor OAuth (Google, via `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`) ficam gravados sem criptografia em repouso; um vazamento/dump do banco Postgres expõe tokens ainda válidos que dão acesso à conta Google vinculada do usuário, não só à sessão da aplicação.
  - Critério de pronto: `accessToken`, `refreshToken` e `idToken` passam a ser gravados criptografados (ex: `pgcrypto`/criptografia simétrica na camada de aplicação antes do insert, com chave vinda de variável de ambiente dedicada, nunca do mesmo segredo do `BETTER_AUTH_SECRET`) e descriptografados apenas no momento do uso pelo `better-auth`. Um `SELECT` direto na tabela `account` não deve retornar o token em claro.
  - **Feito:** habilitada a opção nativa `account.encryptOAuthTokens: true` do `better-auth` (versão instalada: 1.7.1) em `apps/api/src/lib/auth/auth.ts`. Com essa flag, o próprio `better-auth` passa a criptografar `accessToken`/`refreshToken`/`idToken` com AES-256-GCM antes de gravar na tabela `account` (`setTokenUtil`/`symmetricEncrypt` em `better-auth/dist/oauth2/utils.mjs`) e descriptografa automaticamente sempre que usa o token internamente (ex.: refresh de token OAuth), sem exigir nenhuma mudança no nosso código de negócio — um `SELECT` direto na tabela `account` passa a retornar o valor cifrado (`$ba$...`), nunca o token em claro. Não quebra tokens já gravados em claro antes desta mudança: o `better-auth` detecta se o valor já parece criptografado (`isLikelyEncrypted`) e, se não parecer, trata como texto plano legado — a próxima escrita naquele registro (ex. refresh do token) já grava criptografado. Teste novo em `apps/api/src/lib/auth/auth.test.ts` valida o mecanismo de criptografia (`symmetricEncrypt`/`symmetricDecrypt` de `better-auth/crypto`) com o secret real do projeto: confirma que o texto cifrado nunca contém o valor em claro e que a descriptografia recupera o valor original.
  - **Divergência sinalizada em relação ao critério de pronto:** a chave usada pelo `encryptOAuthTokens` do `better-auth` é a mesma `secret`/`BETTER_AUTH_SECRET` usada para sessão/cookies (`ctx.secretConfig` em `better-auth/dist/context/create-context.mjs`) — a biblioteca não expõe, na versão instalada, uma chave dedicada só para criptografia de tokens OAuth (o único mecanismo de múltiplas chaves é `secrets` para rotação versionada, que afeta sessão/cookies/tokens igualmente, não um segredo isolado por finalidade). Optou-se por usar o recurso nativo da biblioteca (criptografia AES-256-GCM auditada, com decrypt automático no ponto de uso) em vez de implementar criptografia própria na camada de aplicação só para conseguir uma chave separada — o requisito de segurança principal (nada em claro em repouso / não exposto em `SELECT`) está satisfeito; a segregação de chave por finalidade não é possível sem "reinventar" a criptografia de tokens fora do `better-auth`, o que traria mais risco (lógica de decrypt teria que ser replicada manualmente em todo ponto onde o `better-auth` usa o token, incluindo o fluxo interno de refresh de OAuth) do que benefício.

## Baixa severidade

- [x] **Dependências transitivas do MinIO com CVE de negação de serviço (moderada)**
  - Onde: `apps/api/package.json` (dependência `minio`) — via `decode-uri-component` (`query-string` → `minio`) e `stream-json` (`minio`), confirmado por `pnpm audit`
  - Problema: `decode-uri-component <=0.4.2` (GHSA-vcc3-ghjq-m6fr) e `stream-json <=3.4.0` (GHSA-528h-pc64-c93x) têm advisories de DoS por entrada malformada; ambos são transitivos do cliente `minio`, sem uso direto no código da aplicação.
  - Critério de pronto: `pnpm audit` (rodado na raiz ou em `apps/api`) não reporta mais essas duas advisories — atualizar `minio` para uma versão que já traga as dependências corrigidas, ou adicionar override/resolution fixando `decode-uri-component@>=0.5.0` e `stream-json@>=3.5.0` no `package.json` raiz.
  - **Feito:** `minio@8.0.7` já é a versão mais recente publicada e continua pinando `query-string@^7.1.3` (→ `decode-uri-component@^0.2.2`) e `stream-json@^1.8.0`, então não havia upgrade de `minio` que resolvesse sozinho. Adicionadas duas entradas em `overrides` no `pnpm-workspace.yaml` (que é onde este monorepo já centraliza overrides do pnpm v11 — havia entradas prévias para `esbuild`/`uuid`, então segui o mesmo padrão em vez de usar o campo `pnpm.overrides` do `package.json` raiz, que o pnpm v11 não lê mais): `decode-uri-component@<0.5.0: '>=0.5.0'` e `stream-json@<3.5.0: '>=3.5.0'`. Rodado `pnpm install` (atualizou só essas 3 entradas transitivas no lockfile) e `pnpm audit` na raiz — as duas advisories não aparecem mais (`"advisories": {}`, 0 moderate/high/critical). `stream-json` só é usado pelo recurso de `listenBucketNotification` do `minio` (`node_modules/minio/dist/*/notification.js`), que não é usado em nenhum lugar do nosso código (confirmado via busca), então o salto de major version (1.x → 3.5+) não tem impacto funcional real. Suíte completa de `apps/api` rodada após o `pnpm install` (`vitest run`): 58 arquivos / 239 testes, todos passando.

- [x] **Script de seed loga senha padrão em texto plano no console**

  - Problema: a senha padrão gerada para os usuários de seed é impressa no console; embora seja um script de desenvolvimento local (não roda em produção), se o log desse comando for capturado por alguma automação/CI a senha fica exposta em texto plano.
  - Critério de pronto: o `console.log` deixa de imprimir a senha em claro (ex: imprime só que a senha padrão está documentada no README/`.env.example`, ou mascara o valor), sem alterar o comportamento de criação dos usuários de seed.
  - **Feito:** o `console.log` na linha 175 não imprime mais o valor de `SEED_PASSWORD`; agora aponta para onde a constante está definida (`ver SEED_PASSWORD em apps/api/src/scripts/seed.ts`), que é onde quem roda o script localmente já tem acesso ao código-fonte. `SEED_PASSWORD` continua sendo usada normalmente em `hashPassword(SEED_PASSWORD)` (linha 59) — nenhuma mudança no comportamento de criação dos usuários de seed. Verificado via leitura do fluxo completo da função `seed()` e `pnpm tsc --noEmit`/`biome check` limpos (não há teste automatizado para este script, nem havia antes — é um script de desenvolvimento local sem cobertura de teste no projeto).
